# US-002: Apply the Forever In-Memory Patch

## As a

wowforever project maintainer

## I want

the Forever patch to be reliably applied to the game process and maintained,
without external tools or `root`

## So that

the client accepts the `auth.gpon.com.co` portal, can log in to Classic Forever,
and the patch can be reused by the final APK.

## Use Cases

| ID | Use Case | Actor |
|---|---|---|
| US-002-UC-001 | Apply the patch to a running process (`scan` + `ensure`) | Operator |
| US-002-UC-002 | Maintain the patch if the client recreates the key store | Patcher |
| US-002-UC-003 | Check whether the patch is applied without writing (`scan`) | Operator |
| US-002-UC-004 | Apply it from the launcher to the process it started (same UID, no root) | Launcher |

## Acceptance Criteria

| ID | Criterion |
|---|---|
| US-002-AC-001 | The patcher loads keys and contract data; it does not hard-code them. |
| US-002-AC-002 | It locates the key store using the anchor-group key and validates the entire store. |
| US-002-AC-003 | It accepts any first padding byte at offset 37, including `7F 00 00`, `00 00 00`, and `07 00 00`; offsets 38–39 must be zero. |
| US-002-AC-004 | After patching, **only** the 32 bytes of the group 8 key change. |
| US-002-AC-005 | The group 1 anchor key is **never** modified. |
| US-002-AC-006 | Reapplying the patch makes no change and reports that it is already patched. |
| US-002-AC-007 | A block with inconsistent flags, IDs, or keys is **not** treated as the key store. |
| US-002-AC-008 | `scan` never writes. |
| US-002-AC-009 | Scanning reads bounded chunks and survives regions that become unreadable. |
| US-002-AC-010 | The functional non-capture Android store scan visits only regions satisfying the existing private writable anonymous apply-mapping predicate (RW or RWX), in stable address order. It preserves bounded reads, overlap, cancellation, identity checks and forward progress when resuming or observing map changes. Coverage is explicitly limited to these eligible regions, not all readable memory; scan never authorizes a write or proves global uniqueness. Capture and CLI behavior remain unchanged. |

## Edge Cases

- The key store reappears with the original key after reconnect and must be patched
  again.
- The anchor key occurs outside the key store (false positive); reject it if full
  block validation fails.
- A candidate block crosses an unmapped-region boundary; reject it.
- The client changes permissions or releases a region during scanning; skip that
  region and continue.
- Different first padding bytes can coexist in one build; byte 37 does not identify
  the key store. Bytes 38–39 must be zero.

## Functional Requirements

### US-002-FR-001

- **Derives from:** US-002-AC-001

THE SYSTEM SHALL load key-store constants (size and entry count, target and anchor
groups, expected flags, historical padding samples, alignment, the 12 known keys,
and the new key) from `forever/contract.json`.

### US-002-FR-002

- **Derives from:** US-002-AC-002, US-002-AC-008, US-002-AC-009

The historical core scanner/writer SHALL be restricted to private, writable,
non-executable, non-file-backed regions. The functional Android diagnostic reader
may inspect all readable regions, but that fact SHALL NOT authorize writes. Its
explicit apply operation SHALL accept only a revalidated block in the launcher's
own child process, in private readable/writable memory (RW/RWX), not file-backed
or shared memory, and SHALL NOT change memory protections. It SHALL preserve
process/mapping identity and honor cancellation before writing; an incomplete scan
does not establish global uniqueness.

In the functional bridge, apply SHALL receive only the active lease token, never
addresses or bytes from the caller. It SHALL require one observed candidate in the
same process, reread and validate all 480 bytes, and confirm the mapping is still
valid. Capture and scan remain read-only. After applying, the full reread SHALL
match the pre-write block except for the group 8 key. A partial write or failed
postcondition SHALL report the number of bytes actually written and prevent further
applications under that lease; it SHALL NOT blindly restore memory that may have
changed.

### US-002-FR-003

- **Derives from:** US-002-AC-002

THE SYSTEM SHALL locate the anchor-group key using the contract's alignment and
calculate the block start from each occurrence.

### US-002-FR-004

- **Derives from:** US-002-AC-002, US-002-AC-007

THE SYSTEM SHALL validate the entire block before treating it as the key store:
IDs `1..entry_count` in order, expected flags, accepted padding, and matching known
keys. For the target group, it SHALL accept either the known key or the new key so
that reapplication is supported.

### US-002-FR-005

- **Derives from:** US-002-AC-003

WHEN validating an entry's padding, THE SYSTEM SHALL accept any value for byte 37
and require zero in bytes 38–39. The `padding_after_flag.accepts` list in the
contract contains historical samples, not an exhaustive list of runtime-accepted
values. This rule does not change validation of the flag at byte 36, IDs, or keys.

### US-002-FR-006

- **Derives from:** US-002-AC-004, US-002-AC-005

WHEN applying the patch, THE SYSTEM SHALL write only the 32 bytes of the target
group's key, leaving the ID, flag, padding, and all other entries unchanged.

### US-002-FR-007

- **Derives from:** US-002-AC-006

THE SYSTEM SHALL be idempotent: if the target key is already the new key, it SHALL
write nothing and SHALL report that the key store is already patched.

### US-002-FR-008

- **Derives from:** US-002-UC-002

THE SYSTEM SHALL provide a maintenance operation that repeats passes at a
configurable interval, supports external cancellation, and reapplies the patch if
the client recreates the key store.

### US-002-FR-009

- **Derives from:** US-002-UC-003, US-002-AC-008

For each key store found, the CLI SHALL report its address and whether it was
already patched. The functional Android bridge SHALL keep addresses internal and
expose only state, counters, and apply results; it SHALL NOT log memory bytes,
keys, addresses, or session data.

### US-002-FR-010

- **Derives from:** US-002-UC-004

THE SYSTEM SHALL NOT require `root` when the target process belongs to the same
user (the launcher-owned game process).

### US-002-FR-011

- **Derives from:** US-002-AC-009, US-002-AC-010

WHEN the functional non-capture Android scan starts or resumes a pass, THE SYSTEM
SHALL visit only regions matching the existing apply-mapping predicate for private
writable anonymous memory, retaining RW and RWX and stable address order. The scan
SHALL resume using its saved address, retain unread chunks and overlap across budget
boundaries, and preserve forward progress after eligible mappings change. It SHALL
invalidate old candidates upon observed eligible mapping changes as before; newly
inserted or reclassified eligible regions behind the cursor may be visited in the
next pass. Each ended pass SHALL allow the next poll to revisit eligible memory.

Coverage reporting SHALL explicitly identify the apply-eligible scope. A completed
pass SHALL NOT claim all-readable coverage or global uniqueness. Other readable
regions SHALL NOT delay this mode by forming a fallback traversal. This scope change
SHALL NOT change write authorization, full-block validation, process ownership,
budgets, cadence, capture behavior or the CLI.

## Non-Functional Requirements

| ID | Requirement |
|---|---|
| US-002-NFR-001 | The core uses no `unsafe`; its logic is pure over a memory abstraction. |
| US-002-NFR-002 | Scanning bounds memory use by reading chunks rather than loading the entire heap at once. |
| US-002-NFR-003 | No write occurs outside the validated target key's 32 bytes. |
| US-002-NFR-004 | The logic is testable without a device or real process. |
| US-002-NFR-005 | An unreadable region or invalid candidate does not abort the entire scan. |

## Assumptions

- The key store is in private writable heap memory, not in a file mapping.
- Contract alignment is interpreted against the **absolute address**; because
  regions are page-aligned, relative reads preserve the same alignment.
- The client may recreate the key store, which motivates the maintenance operation.
- The user approved the read-order experiment and its full fallback on2026-10-22;
  see [the execution plan](../planning/patch-search-priority-plan.md). A speedup
  remains a hypothesis until measured on the device.
- The padding correction is based on the WoW 70450 incident in `wowserver` and its
  corrected validator, with x86-64 login confirmed. The user approved adopting this
  rule in this project; it does not by itself prove that the key store exists in the
  ARM64 client.

- The user replaces the earlier full fallback on2026-10-23 ("si, hagamos eso") with
  apply-eligible-only functional discovery and observational measurements; see the
  [approved comparison plan](../planning/patch-discovery-parity-plan.md). Speedup
  remains unproven until measured on the device.

## Open Questions

- Does the target build recreate the key store after `reason 24`, or is one pass
  sufficient? The upstream launcher reapplies; confirm against the real client.
- Which Android memory-access mechanism is used from the launcher to its own child
  (`/proc/<pid>/mem` or another supported path)? Record the evidence for the
  selected path; do not weaken validation to accommodate a mechanism.
