# US-006: Protected Autologin from the APK

## As a

user of the functional Android launcher

## I want

to save my credentials and explicitly enter them using the game overlay, choosing
whether to remember them

## So that

I do not have to re-enter them on every launch without exposing them in game files.

This records UX5 and step 5 of the approved plan, reaffirmed with “continue with
autologin.” Testing with the prior temporary account was authorized; its ephemeral
secret was deleted and must not be reconstructed from logs. See the
[autologin plan](../planning/launcher-autologin-plan.md).

## Use Cases

- **US-006-UC-01**: Enter, enable, remember, or forget credentials in Settings.
- **US-006-UC-02**: Request one assisted attempt with the overlay account button,
  including with the separately enabled Forever writer while memory capture is off.
- **US-006-UC-03**: Cancel or return to manual entry when session checks fail or
  an error occurs.

## Acceptance Criteria

- **US-006-AC-01** (UC-01): opt-in is off initially; credentials remain in memory
  by default and are persisted encrypted only after explicit “Remember” consent.
  Delete/disable controls are accessible. Saving does not enable autologin;
  disabling autologin retains the account and Forget deletes it.
- **US-006-AC-02** (UC-01): neither secrets nor screenshots of populated forms
  appear in logs, WTF files, arguments, clipboard, intents, backups, or persistent
  UI state.
- **US-006-AC-03** (UC-02): an accessible “Introducir cuenta” icon beside the
  keyboard sends username → Tab → password → Enter only when explicitly tapped,
  independently of the automatic-login preference. Help requires an empty focused
  Username field and no dialogs; the user checks these conditions and manually
  clears any remembered username. The APK checks the current owned session/window
  and observable focus, not internal fields or modals. A wrong field can expose
  secrets; this is assisted entry, not a readiness detector. No screenshots,
  startup trigger, automatic clearing, or additional confirmation dialog are used.
  The entire credential pair must be representable faithfully before any input;
  otherwise nothing is sent. Without usable credentials, inform without input.
  At most one assisted attempt occurs per launch, consumed before first input.
  The separately opted-in Forever writer does not prevent this attempt;
  memory capture remains incompatible. Neither opt-in enables the other, and
  verified patch application is not a prerequisite for submitting the form.
- **US-006-AC-04** (UC-03): closure, observable focus/session/window or geometry
  changes, and real manual interaction during sending cancel further input without
  retry or rearming, including after partial input or Activity recreation. The
  initiating icon tap does not cancel itself. Internal field/modal changes are not
  detectable; there is no automatic readiness wait or 90-second readiness timer.
- **US-006-AC-05** (UC-01, UC-03): invalid key/corruption requires re-entry; there
  is no plaintext fallback or silent recovery of old credentials.
- **US-006-AC-06** (UC-02, UC-03): leaving the form or submitting is not presented
  as successful authentication or gameplay; manual entry remains available.

## Edge Cases

- Activity is recreated, a callback arrives late, or two button taps race.
- Login is visible behind a modal from the same client; unrelated windows/prefixes.
- “Remember” is disabled, key is lost, file is truncated, symlinked, or has a stale
  temporary file.
- The user taps with another field focused or a prefilled username: assisted entry
  cannot detect this; explain the risk rather than claiming semantic verification.

## Functional Requirements

### US-006-FR-001

- **Derives from:** US-006-AC-01
- **Pattern:** Event-driven

WHEN the user saves credentials, THE SYSTEM SHALL keep them only in memory unless
encrypted persistence is explicitly enabled, and SHALL remove prior stored state
when the user forgets the account or disables encrypted persistence. Disabling
automatic submission alone SHALL retain the account.

The approved close-out plan correction states that saving the account is
independent of enabling autologin. Disabling automatic submission does not delete
the account; Forget does. On reopen, the username/state is restored, not a visible
password. An empty password submitted for the same username retains the saved
password; it is not associated with a new username.

### US-006-FR-002

- **Derives from:** US-006-AC-02
- **Pattern:** Ubiquitous

THE SYSTEM SHALL prevent secret exposure in game configuration, diagnostics,
intent transport, persisted snapshots, and backups.

### US-006-FR-003

- **Derives from:** US-006-AC-03
- **Pattern:** Conditional

WHEN the user taps the overlay account icon, IF the current owned session/window
and observable focus are valid and usable credentials are available, THE SYSTEM
SHALL acquire a temporary credential copy, validate the entire pair's faithful
representability before input, and permit at most one assisted attempt per launch.
THE SYSTEM SHALL consume that attempt before first input, revalidate observable
session/window/focus/geometry before subsequent input, and send username, Tab,
password, Enter through the internal input path without clipboard, arguments,
intents, or files. Saving credentials or launching the game SHALL NOT trigger input.
The icon SHALL operate independently of the automatic-login preference and SHALL
explain the required empty focused Username field with no dialogs. Internal
field/modal confirmation remains the user's responsibility, not an APK assertion.

The independent Forever writer opt-in SHALL NOT block this permission; memory
capture SHALL block it. Assisted entry SHALL NOT enable the writer or require prior
patch application. This clarification follows the approved
[correction plan](../planning/launcher-autologin-correction-plan.md).

### US-006-FR-004

- **Derives from:** US-006-AC-04
- **Pattern:** Event-driven

WHEN closure, an observable identity/window/focus/geometry change, or real manual
intervention occurs during sending, THE SYSTEM SHALL cancel further input without
rearming that launch, including after recreation or a late callback. The initiating
icon tap SHALL NOT count as intervention. Internal field/modal changes SHALL NOT
be presented as detectable, and no automatic readiness wait SHALL be introduced.

### US-006-FR-005

- **Derives from:** US-006-AC-05
- **Pattern:** Event-driven

WHEN credential-store integrity or recovery fails, THE SYSTEM SHALL clear the
session, independently attempt to delete the file and key, and request re-entry.

### US-006-FR-006

- **Derives from:** US-006-AC-06
- **Pattern:** Ubiquitous

THE SYSTEM SHALL distinguish submission, authentication, and gameplay, and SHALL
leave manual entry available when assisted entry cannot proceed.

## Non-Functional Requirements

- **US-006-NFR-001**: use one owner per launch and callbacks safe against concurrent
  double-tap, recreation, and late delivery; consuming or cancelling an assisted
  attempt must not allow another attempt in that launch. Do not fabricate automatic
  form/field evidence or apply the automatic readiness deadline to assisted entry.
- **US-006-NFR-002**: use AES-GCM with a fresh IV from the Keystore provider and a
  bounded payload in `noBackupFilesDir`; exceptions and `toString` must contain no
  secret.
- **US-006-NFR-003**: delete owned temporary copies when done; do not promise
  absolute erasure of internal JVM/IME/crypto buffers outside the app's control.
- **US-006-NFR-004**: no root, TLS bypass, executable/runtime changes, or permanent
  system permissions; conduct a security review before enabling the feature.

## Assumptions

- The user authorizes a temporary account, not real accounts or recovery of deleted
  secrets.
- Secrets shown in Settings editors are transient; they are not stored in
  `rememberSaveable` or exported when restoring UI state.

## Open Questions

- Assisted-entry requirements and test cases are approved. C138 implementation is
  preliminary and hard-disabled pending privacy remediation and independent
  security/input review. The earlier worker variant failure is historical: a later
  retry starts successfully. Synthetic controller tests do not establish transport
  fidelity on the device or protection of all diagnostic sinks.

- The approved nonvisual approach has no confirmed direct form/field signal in
  the examined XServer APIs. Another client/runtime integration needs evaluation
  and scope approval; see the [investigation](../../docs/launcher-autologin-investigation-2026-10-22.md).
- Historical code 79 UI review approved a clarity correction: Account explains
  manual login and keeps editing/Remember/Save disabled until the flow can be
  enabled reliably, while Forget remains available. This does not alter the future
  autologin contract or make credential-store tests equivalent to end-to-end
  acceptance.
- Positive form/field evidence with geometry and negative cases was not available
  in code 69. Window metadata and an old host reference are insufficient.
- A temporary account was received and authorized; its private file was created
  and deleted without submission. Account information is not missing; form/focus
  evidence remains the blocker.
- Real Android Keystore and protected UI/capture behavior require device validation;
  JVM tests with a JCE backend are not equivalent to testing the Android provider.
