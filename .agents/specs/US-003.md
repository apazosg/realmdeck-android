# US-003: Prepare and Launch Forever on Android

> **Pending reconciliation (2026-10-23):** the user approved Wi-Fi-only for all
> app downloads. AC-08 records the provisioning impact; FR-008 derives the policy
> and was approved on 2026-10-23. TC-008 was approved with all derived cases on
> 2026-10-23. Implementation/validation are in progress; existing NFR remain applicable.

## As an

Android ARM64 user

## I want

to prepare and launch WoW Classic Beta for Classic Forever from one app

## So that

I do not need Battle.net, a PC, root, ADB, or manual Wine configuration.

This story records the scope and seven approved criteria from
`automated-arm64-launcher-plan.md` (approved 2026-09-30). It does not expand
US-001 or change its x86-64 defaults, and it applies US-002 without weakening its
validation. The C127 trial on the xaga/Mali device later reached the Classic
Forever login, and the user confirmed entry into the game with client build
1.60.1.70450. This is a device- and build-specific observation; it does not
establish sustained gameplay, a broad compatibility matrix, or a general release.
See [`docs/launcher-app-status.md`](../../docs/launcher-app-status.md) for the
dated evidence and limitations.

## Use Cases

- **US-003-UC-01**: Prepare and launch from a new or reusable installation.
- **US-003-UC-02**: Cancel, retry, and recover an interrupted operation.
- **US-003-UC-03**: Inspect and export the result of a particular run.

## Acceptance Criteria

- **US-003-AC-01** (UC-01): one action executes the required stages; there are no
  manual container or probe steps. Duplicate start actions do not duplicate work.
- **US-003-AC-02** (UC-01, UC-02): only verified resources from the pinned catalog
  are reused; network errors, corruption, or insufficient disk space do not produce
  a valid state.
- **US-003-AC-03** (UC-01): the system attempts to run the verified ARM64 PE with
  `-config BetaSuspendedTest.wtf -d3d11`, recording the runtime context and actual
  process.
- **US-003-AC-04** (UC-01): the portal comes from the contract; the group 8 write
  occurs only after validating the complete key store and the owned descendant's
  identity.
- **US-003-AC-05** (UC-02, UC-03): errors retain their stage and evidence even if
  the guest produces no logs; interruption prevents late launches.
- **US-003-AC-06** (UC-03): SAF exports exactly the selected run, including its
  journal, hashes, bounded output, and available historical evidence, without secrets.
- **US-003-AC-07** (UC-01, UC-03): preparation, process start, rendering, and login
  are distinguished; the APK contains no client or proprietary CASC data.
- **US-003-AC-08** (UC-01, UC-02): app-managed runtime/client provisioning and its
  metadata use Wi-Fi only. Without usable Wi-Fi, required downloads wait or pause
  with a clear explanation; loss of Wi-Fi cannot fall back to cellular traffic.
  Durable verified resources are preserved for retry under existing validation
  and cancellation rules. A fully prepared local installation is not denied Play
  solely for lack of Wi-Fi. This does not constrain the running game's traffic.

## Edge Cases

- Timeout or cancellation while preparation completes; callback from another run.
- Android dies before spawn, or Wine exits before producing a log.
- PID reuse, same UID without parentage, or game identity not established.
- ARM64 key store is absent or incompatible; signatures must never be weakened to
  force a patch.
- Catalog is incomplete, path is unsafe, download is truncated, or HTTP range is
  ignored.
- The Activity is recreated while SAF is open or preparation continues.

## Functional Requirements

### US-003-FR-001

- **Derives from:** US-003-AC-01
- **Pattern:** Event-driven

WHEN the user requests preparation and launch, THE SYSTEM SHALL orchestrate a
single run of runtime setup, provisioning, configuration, and startup without
passing through a game library.

### US-003-FR-002

- **Derives from:** US-003-AC-02
- **Pattern:** Ubiquitous

THE SYSTEM SHALL verify resources from the pinned ARM64 catalog before promoting
them and SHALL reuse resources already verified when retrying.

### US-003-FR-003

- **Derives from:** US-003-AC-03
- **Pattern:** Event-driven

WHEN preparation is verified, THE SYSTEM SHALL launch `WowB-ARM64.exe` with the
approved flags and persist argv, cwd, runtime, and spawn result.

### US-003-FR-004

- **Derives from:** US-003-AC-04
- **Pattern:** Ubiquitous

THE SYSTEM SHALL obtain the portal and keys from the canonical contract, modify
only `WTF/BetaSuspendedTest.wtf` for Forever configuration, and apply US-002 only
to an owned process whose identity and key store have been validated.

### US-003-FR-005

- **Derives from:** US-003-AC-05
- **Pattern:** Event-driven

WHEN an operation is canceled, fails, or is interrupted, THE SYSTEM SHALL retain
its stage and evidence and SHALL reject later callbacks or launches from that run.

### US-003-FR-006

- **Derives from:** US-003-AC-06
- **Pattern:** Event-driven

WHEN a report is exported, THE SYSTEM SHALL export the run identifier selected
when SAF was opened, even if the screen or app state changes.

### US-003-FR-007

- **Derives from:** US-003-AC-07
- **Pattern:** Ubiquitous

THE SYSTEM SHALL distinguish observed states from unverified capabilities; a
provisioning pass or synthetic memory result does not constitute evidence of
rendering or Classic Forever login.

### US-003-FR-008

- **Derives from:** US-003-AC-08
- **Pattern:** State-driven

WHILE app-managed runtime/client provisioning requires or performs network work,
THE SYSTEM SHALL restrict its connections to usable Wi-Fi, including metadata and
background resource preloads. Without usable Wi-Fi it SHALL wait or interrupt
downloads with a clear explanation, without cellular fallback. Retry SHALL reuse
only durable verified resources under FR-002 and SHALL retain FR-005's cancellation
and late-launch protections. Fully prepared local Play SHALL NOT require Wi-Fi;
the running game's traffic is outside this policy.

## Non-Functional Requirements

- **US-003-NFR-001**: transfer and disk use are estimated before downloading; a
  full download of tens of gigabytes requires separate informed authorization.
- **US-003-NFR-002**: I/O, decompression, and scanning run off the UI thread; memory
  use is proportional to working windows, not the full catalog of millions of
  objects.
- **US-003-NFR-003**: logs are bounded per run and contain neither credentials nor
  the complete process environment.
- **US-003-NFR-004**: cleanup is limited to owned jobs and processes; unknown
  identity blocks another run or write and never authorizes a global kill.

```gherkin
  Given the client and runtime are verified
  When the game spawn fails
  Then the report contains the stage, command, and startup error

# US-003-TC-004 (validates US-003-FR-004)
Scenario: Do not write to an unowned process or invalid key store
  Given the PID is not owned or the key-store block is incompatible
  When Forever compatibility is requested
  Then memory is not modified
  And the rejection is reported

# US-003-TC-005 (validates US-003-FR-005)
Scenario: A canceled preparation completes late
  Given a run has been canceled
  When its preparation callback arrives
  Then no new process is started

# US-003-TC-006 (validates US-003-FR-006)
Scenario: SAF selection remains bound to one run
  Given SAF was opened for a selected run
  When the screen is recreated before saving
  Then that same run is exported or an error is reported

# US-003-TC-007 (validates US-003-FR-007)
Scenario: Successful preparation does not claim login
  Given all resources are verified
  And no game-login evidence exists
  When the run report is inspected
  Then rendering and login remain unverified

# US-003-TC-008 (validates US-003-FR-008, US-003-FR-002, US-003-FR-005)
Scenario: Provisioning and background preloads use only Wi-Fi
  Given cellular is available without usable Wi-Fi
  When preparation or a background resource preload requires network resources
  Then downloads wait with an explanation and no request uses cellular
  When eligible Wi-Fi downloads start and Wi-Fi is then lost
  Then no transfer falls back to cellular and durable verified resources remain
  And cancelled runs cannot produce a late launch
  And retry reuses only verified resources under the existing guards
  And fully prepared local Play does not require Wi-Fi
```

  validated on the phone and cannot be inferred from bootstrap size alone.
- The user approved retaining the experimental package signature and current
  components.
